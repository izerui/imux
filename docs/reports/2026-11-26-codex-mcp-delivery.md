### 候选常驻指引

> 沿用你已有的工作方式和项目约定。JetBrains IDE 额外提供项目索引。遇到同名符号、接口分派、重写或跨模块用法，且答案会改变实现或审查结论时，用 `imux_code` 查清相应关系。按当前问题选择查询方向和深度。索引报告覆盖不完整时，可结合源码、配置、日志或实际执行补证。IDE 重构、检查和调试也可按需要使用。交付时按用户要求的实际结果选择验证方式。

这是主智能体同时挂载两类工具时的候选文案。生产版本应继续按实际挂载能力生成文本，只读角色另行保留权限约束。其效果仍需测量。

### 怎样知道两类工具互补成功

两个宿主分别做四组独立对照，包括原生工具、只增加工具、增加工具和现行指引、增加工具和候选指引。每组使用相同的固定代码版本、模型、权限和时间预算，同一道题独立重复，并随机化顺序。验收者先写好评分表，再匿名评首版产物。题目要同时测出三个方向的效果。

- **语义查询能带来多少增益。** 改一个有多个实现、另有同名无关方法的接口。看真正的调用方是否都正确更新，以及无关方法是否保留原行为。
- **原有强项是否保持。** 处理一个源自旧配置或真实输出文件的错误。看能否利用样本复现、给出正确结果、覆盖已有数据，以及发现用户没有点名的相邻失败条件。
- **同一任务能否接力。** 修改一项经接口分派的导出功能，实际输出还受字符串配置控制。索引可以定位实现，文件和运行结果才能确认配置生效。用真实调用与导出文件验收两端。

首要指标是每组的首版必需项覆盖率、严重遗漏、误改和实际验证通过率。另记主动找到并复核的有效问题，避免靠多报猜测得高分。只有在语义任务收益提高、原生任务质量保持、混合任务遗漏减少时，才能据此支持默认启用候选指引。工具调用率和 Token 仅用来解释成本。本报告已有的运行数据来自 Codex 单题只读实验，Claude Code 和四组跨任务行为结论仍待实测。

2026-11-26。本次评测采用一条真实交付记录和同一工作区的只读对照实验。用户关心的是第一次交付能否兑现明确要求，同时主动覆盖可预见的问题。工具调用次数只用于还原过程。

## 判断

就这次返工而言，最有力的解释是首次交付的验收方式与用户目标不匹配。用户已经选定可交互原型，首版交付列出了测试和兼容性结果，同时明确写出尚未在 IDE 里手动验收外观。用户随即指出差距。随后，同样装着 MCP 的环境能渲染实际组件、检查展开与搜索、测量右边缘坐标。工具环境具备查出这些问题的条件。

历史记录不支持“调用新方法挤掉了第一次实现工作”的解释。它仍允许另一种解释：随工具注入的指引改变了注意力和完成标准。小规模对照确实观察到工作路径、成本和问题选择的差异，尚不足以判定两种配置在首次实现质量上的平均胜负。

## 如何作配置决定

对于这个用户，现有证据支持继续保留语义查询能力，同时优先检验插件工作指引。可先用一条验收原则做下一轮配置对照：“先确定用户从哪里进入、最终看到什么。按原型的任务对照真实画面，跨数据源的任务走一次真实入口。编译、检查、测试分别说明验证到了哪一步。”工具选择仍按问题决定。这样下一次比较能直接观察用户是否少返工。

要判定哪组更容易一次实现到位，建议用预先保留的起始版本和验收表，至少覆盖原型还原、跨文件重构、真实数据接入三种不同任务。每个配置独立重复，固定模型、时间预算与权限，将首版成果匿名交给同一位验收者。主要指标用首版必需项通过率、用户必须再提醒的项数，以及主动补到且经验证的问题数。把工具次数、耗时和 Token 留作解释质量差异的辅助指标。本次同题实验只测源码审查，各组看到的也是多轮修正后的源码，不能回推它们当初会写出怎样的第一版。
