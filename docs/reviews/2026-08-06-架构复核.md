# 架构复核（2026-08-06）

## 范围与方法

覆盖 `src/main/kotlin` 全部 31 个文件（主源码 3354 行，测试 2959 行）。

方法：先由两个 subagent 分别通读「session 数据层 + turn 轮次层」与「terminal 平台层 + toolwindow UI 层」，
再由主会话逐条复核其结论——**结论以复核为准**。首轮转述未经核实，其中两条被证伪、一条严重性被低估，
本文记录的是复核后的定论。

## 总评

分层与依赖方向干净：`turn → session → model`，`monitor` 居顶，无循环依赖、无层次颠倒。

三项明显强于同类插件：

- **纯逻辑与 IO 分离彻底**。`TurnSignalParser`、`RunningSessions`、`CompletionSubtitle`、
  `RuntimeStatusTracker`（时钟注入）、`SessionListModel`（scan/clock 双注入）全部可离线单测；
  各 Reader/Index 一律构造器注入 home 路径。
- **平台集成规范**。全部走官方扩展点，无反射、无改文件名冒充标题、无 `WriteAction` 改只读 VFS，
  且有 `PlatformApiAlignmentSourceTest` 做源码级约束。
- **注释解释「为什么」并带实测数据**。正则栈溢出、64KB 尾窗口、8535 条记录的 stop_reason 分布——
  这是决策记录，不是复述代码。

问题都是局部的，没有系统性失控。

## 逐条结论

### 1. 双通知：两套完成检测跨轮询拍触发（最该修）

`SessionMonitor.kt:190`：

```kotlin
val completed = (statusTracker.completedSince(snapshot) + watcher.poll()).distinct()
```

`distinct()` 只去重**同一次调用内**的重复，而两个来源是异步的：`TurnWatcher` 在读到
`stop_reason != tool_use` 时报完成，`RuntimeStatusTracker` 要等运行态文件的 `status` 跃迁。
轮询 1 秒一拍（`SessionStoreWatcher.kt:124`），两个信号一旦跨拍，`distinct` 就兜不住。

后果：`completed.forEach` 里的 `TurnNotifier.notifyCompleted`（`SessionMonitor.kt:211`）无条件调用，
弹出第二个气泡。`markUnread` 是幂等的，所以只有通知重复。

`TurnNotifier.kt:57` 的 `active[sessionId] = notification` 直接覆盖且不 expire 旧通知，
于是两个气泡同时挂着。

**与 `shell` 状态同源**：修复前，claude 会话只要带后台 shell，`status` 要几分钟后才转 `idle`，
与 `TurnWatcher` 必然跨拍，即必然双通知。把 `busy -> shell` 也算完成之后，两个信号被拉到同一时刻附近，
撞进同一拍的概率大增——压低了触发概率，没有根治。

根治方向：完成判定应有单一权威来源，或在 `SessionMonitor` 侧按 sessionId 做跨拍去重（带 TTL）。

### 2. `SessionStoreWatcher` 与 `JsonLineScanner` 无测试

`SessionStoreWatcher` 已经为可测性注入了 `today` / `intervalMs` / `slowEveryTicks`
（`SessionStoreWatcher.kt:44-47`），`signature()` / `watchedDirs()` 也是 public——
设计留足了口子却一个测试都没写。

`JsonLineScanner` 被 4 个类依赖，注释明确说它替代的正则实现会栈溢出，同样无直测。

其余 11 个无同名测试的类是 UI/平台类，难以脱离平台运行，且部分已被
`PlatformApiAlignmentSourceTest`、`AgentSessionTreeIconTest` 覆盖片段，可接受。

### 3. `applyNewBindings` 寄生在 UI 渲染里（设计债）

`drainNewBindings()` 全项目唯一的生产调用点在 `AgentSessionTree.applyNewBindings`
（`AgentSessionTree.kt:320`），而它挂在渲染入口 `reload()` 的第一行（`:236`），且是破坏性读取。
一个核心状态迁移（pending key → 真实 sessionId）被绑在 Swing 树的重绘上，
与 `SessionMonitor.kt:58-63` 自己确立的「界面可有可无」原则相悖。

**但后果有限**：新建会话的 `+` 按钮就长在工具窗口标题栏（`AgentToolWindowFactory.kt:53`），
没展开过面板根本产生不了 pending，正常路径是通的。真实风险只剩 content 被销毁
（侧边栏移除、插件热重载）后恰好发生绑定——此时 `newBindings` 无人消费，
终端与真实会话失联，再点会重开一个终端。

### 4. Codex 用 mtime 作为 lastActiveAt（健壮性隐患）

口径确实不一致：Claude 用文件内时间戳（`ClaudeSessionReader.kt:60`），
Codex 直接用 mtime（`CodexSessionReader.kt:67`），而 `SessionRepository.kt:20` 把两者混在一起排序。

**但当前无实际影响**。实测本机 12 个 codex 会话文件，mtime 与最后一条记录的 timestamp
偏差全部为 0 秒。Claude 拒绝 mtime 的理由是「resume 会追加 `mode`/`permission-mode`
两条无时间戳记录」，codex 没有这个行为——它每条记录都带顶层 `timestamp`。

隐患在于：codex 一旦改行为，或文件被外部工具 touch，就会静默错排。
而 `lastTimestampOf` 本身是 agent 无关的（只找顶层 `timestamp` 字段），
codex 直接调用即可，是一行的改动。

### 5. 风格偏好（不建议单独立项）

- 两个 Reader 无共同接口，`truncate`、`TITLE_MAX`、`"会话 ${id.take(8)}"` 回退、
  `stringOf`/`longOf` 多处逐字重复。
- `TurnNotifier` 是全局 object 持有可变 map，无项目维度。sessionId 是 uuid 撞不上，
  `ClaudeRuntimeIndex` 还按 cwd 过滤过一道，实际无害。
- `TerminalHost` 里的 `scrollToBottom` / `isScrolledToBottom` / `currentTerminalEditor`
  只被 `AgentTerminalFileEditor` 使用，放在 project service 里属错位。
- `SessionListModel` 管 pending、绑定、监听器，本质是 UI 状态机而非会话数据读取，
  放在 `session` 包拉低该包内聚性。
- `AgentSessionTree` 454 行**不是**问题，大半是注释；该拆的是外泄的领域逻辑，不是按行数切。

## 首轮转述中被复核推翻的结论

记录在此，避免日后重复采信。

| 首轮说法 | 复核结果 |
|---|---|
| `RunningSessions` 只传 CODEX 是「硬编码的偏斜」，丢弃了 claude 的 watcher 状态 | **证伪**。这是有意为之且正确：claude 有 CLI 亲自写的一手运行态，优于文件推断。`RunningSessions.kt:10-16` 已写明理由与 codex 的已知盲区 |
| `lastActiveAt` 口径不一致「每次列表排序都在生效」 | **证伪**。实测 12 个 codex 文件偏差全为 0 秒，当前两种口径等价 |
| `applyNewBindings` 会导致「从没展开过面板的项目绑定永不发生」 | **证伪**。新建入口就在工具窗口标题栏，没展开过面板不会产生 pending |
