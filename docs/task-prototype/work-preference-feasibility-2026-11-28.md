# 工作偏好滑块：第一轮可行性实验报告

日期：2026-11-28。

## 结论

实际完成了两轮、共十二次独立开发实验。当前这版引导词没有表现出稳定、清晰的档位效果。

- 十二份实现均通过对应的统一验收。
- 偏向推进组的测试方法数量较少，但不能据此认定节约了时间或成本；其中一次漏测了改错会话的情况。
- 深入核查组的故障检出能力没有超过默认组。
- 因而不能宣布“滑块已验证有效”，也不能由此断定所有工作偏好引导都无效。
- 当前结果支持继续做小范围行为实验，不支持把五个档位宣传成已经有稳定区别的产品能力。

本次只测试了文字偏好对实际开发产物的影响。没有接入真实 CLI 钩子，没有验证中途切换、回到默认、无聊天消息应用或三种 CLI 的一致性。

## 验证方法

使用十二个独立子会话，不继承本次讨论历史，不向执行者展示其他组输出或评测脚本。所有组均使用主会话默认继承的模型配置，没有手动覆盖模型或推理强度。调用接口未返回精确模型构建版本、采样参数及费用，不能据此做跨模型或成本结论。

每轮使用同一份初始代码、同一任务、同一工具环境；三个档位各运行两次：

| 标记 | 档位 | 附加要求 |
| --- | --- | --- |
| a1、a2 | 默认 | 不添加工作偏好 |
| b1、b2 | 优先推进 | 最小完整改动、暂缓可选打磨、没有新证据时检查假设、保留必要验证 |
| c1、c2 | 深入核查 | 核对相关假设、入口、边界与失败路径，提供验证依据，风险覆盖后停止 |

执行者实际修改隔离目录中的 Python 标准库小程序并运行测试。这里使用的是独立实验程序，不是向 Imux 引入 Python 测试；Imux 产品测试仍遵守 JUnit 4 约定。

主会话在执行完成后统一复测：

1. 用外部验收检查公开入口的实际结果。
2. 运行执行者自己的测试套件。
3. 在临时副本中分别注入预先定义的错误，再运行各组测试，看测试是否能发现错误。
4. 检查代码改动和测试内容，避免仅凭执行者的完成汇报下结论。

故障注入的检查脚本在执行者工作期间编写，执行者不可读取。第一轮评测脚本复核时收窄了三个注入错误，避免同时引入不相关故障；统一重跑后结果不变。每个注入版本都经外部验收确认确实违反既有要求或行为。

测试数量包含原有的三个测试方法。一个方法可能包含多个断言或子用例，因此数量不等于覆盖程度。故障检出率也只针对本次有限的错误集合，不是生产质量评分。

## 第一轮：要求明确的修复

任务：修正最近会话与搜索列表的归档过滤、时间排序、同时间稳定顺序、搜索后限量、缺失时间、负数和零数量边界，并保持输入不变。任务把这些要求明确列出。

| 档位 | 外部验收，两次分别计 | 测试方法数 | 检出注入故障，两次分别计 |
| --- | --- | --- | --- |
| 默认 | 20/20、20/20 | 10、13 | 9/10、9/10 |
| 优先推进 | 20/20、20/20 | 9、8 | 9/10、9/10 |
| 深入核查 | 20/20、20/20 | 9、9 | 9/10、9/10 |

六组实现均正确完成任务，改动范围相近。深入核查的两份实现都增加了零数量的提前返回，但没有对应的质量优势证据。

共同测试盲点：同时间的项目应保留输入顺序。六组都写了相关测试，但测试数据里的标识顺序碰巧与字母顺序一致。把实现错误地改成“同时间再按标识排序”，六组自己的测试仍通过；外部验收使用反向标识顺序，能够发现错误。

这不是原始实现有错，而是测试未能防住这一类回归。深入核查引导没有消除该盲点。

任务末尾还有两个关于反复失败和可选重构的问答。三组回答基本相同：先取新证据、暂缓无关重构。这些只是声明的做法，不计为实际行为改善。

## 第二轮：只给症状的开放排错

第一轮可能因为任务过小、要求过明确而不容易区分偏好，故追加第二轮。第二轮在观察第一轮结果后设计，是探索性跟进；不能与第一轮混在一起宣称统计显著。

任务只说明“改名后侧栏已更新，搜索有时仍是旧名字”，由执行者自行检查代码和现有说明，决定修复及验证范围。

程序包含会话存储、缓存搜索、对话框改名、行内改名和可撤销命令。六组都定位到：

- 改名后没有发出已有的变更通知。
- 行内改名绕过了统一写入入口，连带绕过名称校验与通知。

| 档位 | 外部验收，两次分别计 | 测试方法数 | 检出注入故障，两次分别计 |
| --- | --- | --- | --- |
| 默认 | 18/18、18/18 | 8、9 | 7/8、7/8 |
| 优先推进 | 18/18、18/18 | 6、7 | 6/8、7/8 |
| 深入核查 | 18/18、18/18 | 7、8 | 7/8、7/8 |

生产代码修改完全相同：增加一处通知，将行内改名改为调用已有写入方法。所有组都没有扩大成无关重构。

具体区别：

- 优先推进 b1 的测试只构造一个会话。因此把实现改成“有另一个会话时错改另一个”，它的测试没能发现，另外五组发现了。
- 六组都没发现“返回可修改的内部缓存对象”这一注入错误。这属于原有搜索隔离行为的回归探测，不是本次修复已经破坏了该行为，也不能把它当作必须扩大修改范围的理由。
- 深入核查的测试源代码为 107、128 行，默认为 108、115 行；测试代码变长并没有带来更高的本次故障检出率。

## 能说明什么

观察到的事实：

- 本环境能够在同一类实际开发任务中加入工作偏好，并对实际输出做可重复的自动验收。
- 优先推进的测试方法数量在两轮中都少于默认组，但方法组织方式也能造成数量差异，且样本小，不能把它认定为稳定因果效应。
- 默认组本来就采用了小范围修复并进行了较充分验证，可能使额外的温和引导难以体现差异。
- 深入核查没有表现出“更多有效覆盖”的优势。

尚未证明：

- 存在用户能稳定感知的左、中、右差别，更不用说五个档位。
- 偏向推进减少了耗时、token、调用次数或返工。
- 深入核查能减少真实项目中的遗漏。
- 中途改变偏好能改变已经进行中的工作。
- 恢复默认能消除之前偏好对后续工作的影响。
- 相同偏好在 Claude Code、Codex、Pi 中产生相同效果。

限制：只有两个小型合成任务，每种条件每任务两次；共享宿主基础指令；没有固定随机种子，没有完整的运行成本数据。没有长期任务、需求歧义、真实失败循环或大规模修改。本报告是初步试验，不是模型能力评测。

## 对产品设计的建议

保留用户提出的“会话级滑块、中间默认、无独立开关”的交互方向，但把行为效果作为待验证假设。

后续实验优先做：

1. 使用确实存在可选探索、验证成本和交付取舍的真实任务，提前规定哪些属于额外投入。
2. 在同一任务的中途切换偏好，对比后续实际动作；单独验证恢复默认。不能用启动时加提示冒充动态钩子验证。
3. 在偏好生效前固定观察标准：额外检查数量、与风险相关性、可选修改范围、真实成本、质量底线。
4. 先验证左、中、右三个锚点能否区分，再决定是否值得增加中间档位。

不建议通过规定更多测试、强制增加代码量或删减必要验证来“制造差异”。工作偏好应影响合理取舍，不应把质量降级当作左档效果。

从仓库根目录复跑：

```sh
python3 -B .reference/work-preference-pilot-2026-11-28/evaluate.py
python3 -B .reference/work-preference-pilot-2026-11-28/round2/evaluate.py
```

这些命令重新验收已生成的实现及测试，不会重新调用模型。重新运行模型需要按 manifest 和 task 为各组创建新的隔离副本；输出允许变化，不保证复现相同源码。
