# Imux 会话与独立 Codex CLI 的代码分析对照

## 隐性竞态修复盲测

两组从 `3d1244b8` 的独立副本开始，使用相同模型和推理强度。工单只描述手机重连、电脑立即 `/fork` 后偶尔漏掉第一条消息，后续消息正常。原版可确定性复现。轮询恰好在绑定表公布新会话、桥接登记迁移的间隙运行时，会按普通新绑定处理，跳到记录末尾。

| 本轮结果 | Imux 引导词与代码 MCP | 原生 CLI |
|---|---:|---:|
| 完整交付时间 | 247.2 秒 | 187.3 秒 |
| shell 命令 / MCP 调用 | 57 / 0 | 45 / 0 |
| 独立验收 | 10/10 | 10/10 |
| 自行运行的相关 JUnit 测试（据各组报告） | 77 | 60 |

两组都先登记迁移，再在同一把锁内公布新绑定。插件组另加了发送渠道层的回归测试，检查重复轮询后手机渠道只收到一次首条新消息。两份补丁都留在实验副本中。每组各跑一次，时间包含各自选择的测试范围、模型等待和构建环境处理。

独立验收最初的六个用例模拟开关代次，原版有三个失败。核对后发现生产桥接传入固定代次，于是加了四个生产顺序用例，按各版本的迁移入口方法体运行真实绑定表和文件读取器，替代 IDE 与手机外围。原版在冷启动和已有读取位置的两次 fork 上漏首条，文件晚出现及恢复旧会话两项通过。两组最终生产源码都与各自验收副本逐文件一致。验证覆盖本地 JUnit 和模拟发送渠道，真机联调仍待单独验证。

2026 年 11 月 26 日，在同一台 macOS 机器、同一版源码上启动 27 次独立 Codex 会话，20 次成功交付，7 次在模型服务连续返回 HTTP 503 后退出。下表每个数字是一份完整答案的墙钟秒数，从启动 CLI 到进程退出，包括模型等待、工具调用、修改和智能体自己的验证。工作区准备与事后独立验收另计。

**如何理解耗时。** 两次工具上报修改的快慢顺序正好相反。接口题也出现反转。并发运行会共享机器和服务容量，缓存状态随运行变化，秒级差距不足以给两组排稳定名次。第二批出现七次服务失败，分别是插件组四次、原生组三次，失败用时为 51.8 至 64.2 秒。保留这些失败并重跑后，五道题都有双方可核验的交付物。

**工具和提示词的拆分。** 单独拿接口题对照，原生首轮 31.5 秒，只加当前引导词 32.5 秒，只挂代码 MCP 36.6 秒，两者都加 36.3 秒。四份答案都正确。只挂 MCP 的会话最终全用 shell。两者都加的首轮实际用了两次 `type_hierarchy`，分别找父接口、列实现。在九份成功的完整插件组答案中，仅这一份使用了代码 MCP。这个比例描述本次自主选工具的表现，也解释了为什么修改题的成绩无法归功于索引。

**审查质量。** 两边都看出正常异步读取返回时会再次核对会话，切标签也会关窗。原生组还提出在“检查通过、渲染之前”人为插入一次切换。这适合做故障注入，实际 UI 回调在 EDT 中连续运行，答案没有证明用户操作能插入这个间隙。插件组对此表述更审慎。两边提出的同 ID 双标签覆盖和关其他标签误清都有可区分新旧行为的复查步骤。

**修改质量。** 每个写入任务都使用新的本地克隆，只允许改一个目标文件。八份成功补丁均只改了指定文件。独立验收器先在原版触发两处预期断言失败，再对八份补丁逐一运行。它使用 Node 调用真实扩展注册入口，模拟 Pi 事件和 `fetch`。这验证了扩展输出，实际 Pi 安装、IDE 整体构建和跨平台运行仍缺单独样本。

**实验配置与范围。** 两组均使用 `gpt-6.2-astra`、medium 推理强度、相同题面、新会话及同一仓库约定。插件组复用了当前会话传入的引导词与 `imux_code` 服务，未接入 IDEA 构建、交互式调试器、会话管理或手机工具。IDE 索引指向原工程，写入发生在源码起点相同的克隆；八份成功修改均只用 shell 和文件编辑。评测没有改动产品，界面入口、语音触发、三个 CLI 的产品行为、手机桥接、三平台适配、多语言、宣传材料和功能状态进出不涉及。下文为前期探索，计时以本节为准。

每次运行的题面、回答、事件及时间记录保存在本机临时目录 `/tmp/imux-timed-1126-v1`，计时器为 `/tmp/imux-bench-rounds.py`，独立验收器为 `/tmp/imux-bench-accept.mjs`。

## 一处可复查的漏报

在 `SessionInfoTool.kt:34` 的 `perform` 上查 `call_hierarchy(callers, depth=1)`，本轮实际返回 `callers: []`。查 `find_references` 也得到零条引用，但它识别出了父接口 `TerminalNotices.kt:151`。对该接口执行相同的调用方查询，马上返回 `TerminalNoticeOverlay.kt:338` 的 `tool.perform(this@ToolPill)`。最后还需看 `AgentTerminalFileEditor.kt:366` 的对象绑定，才能确认点击信息图标时执行哪个实现。

这给使用者两个判断依据。盘点实现时，索引能直接交付按符号身份区分的清单。同一次调查中，从子类出发得到的空列表容易让人提前下结论。这个案例适合做接口反查的回归样例。工具返回空结果且知道父接口时，也可以把父接口位置带回给调用者。

## 插件组原答

**第二题 · 点击会话信息到底执行谁？** 编辑器把会话信息实例装进共享按钮（AgentTerminalFileEditor.kt 第 366 行）。左键按下时按钮须可用，松开时指针须在按钮内。唯一查到的共享分派点是 TerminalNoticeOverlay.kt 第 338 行。这个按钮执行 SessionInfoTool.kt 第 34 行，最终在第 129 行显示窗口。接口共有六个生产实现，另外五个是结对菜单、澄清对话、工具警告、会话轨迹、手机连接。索引另列三个测试实现。其他实现都不是这一次点击的接收者。

**第三题 · Kotlin 和 JavaScript 两层调用树能证明什么？** 脚本在临时 IDE 工程中直接调用 `CodeNavigator.callHierarchy`（local-callees.groovy 第 39–53 行）。正常 MCP 请求另经 CodeMcpProtocol.kt 第 104 行、CodeMcpService.kt 第 56 行进入同一实现。两种语言都断言深度一的直接目标恰为 `inner`、`inlineBody`，`inner` 的位置标为 `call`，此时无子树。深度二只断言 `inner` 的子目标恰为 `reached`，其余分支未作完整断言。遍历跳过嵌套具名函数体，lambda 的正文归外层，调用目标满足深度等条件才展开（CodeNavigator.kt 第 628、658 行）。例子只创建 lambda，没有调用它。静态树出现 `inlineBody` 不能证明运行时执行。本轮读了脚本和实现，未运行这个隔离 IDE 脚本。
