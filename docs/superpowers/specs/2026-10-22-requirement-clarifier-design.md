# 需求澄清：动手前补上没想到的方向

## 背景

imux 已有的结对编程、单次审查、会话轨迹都作用在**代码写完之后**，目的都是提升 AI 编程效果、减轻人的负担。
需求澄清补上**动手之前**这一环。成功标准沿用最初的定义：
**少问几个问题，却显著减少返工、方向纠正和审查阶段才暴露的问题。**

做一次迭代时，用户往往只写一句话、一段文字或一份需求文档就交给 Agent CLI。总有想不到的方向，有与已有功能
冲突的地方，甚至出发点本身就不对。需求澄清由单次 Agent 结合项目代码找出这些方向性问题，逐个跟用户确认，
最后输出一份调整后的需求，直接发给当前会话的 Agent CLI 执行。

## 最终要求（逐条与用户确认）

1. **定位**：在主 Agent 动手前，结合项目代码找出需求里用户没想到的方向性问题——出发点不对、与已有功能冲突、
   遗漏的关键方向——补充、修正后交给主 Agent。不展开实现细节、不写任务清单：主 Agent 在执行中对代码理解更深入，
   细节由它判断。衡量标准是主 Agent 做得更顺、更优、bug 更少，同时用户被问得尽量少。
2. **输入**：一句话、一段文字或一个需求文档路径（Agent 自己读取文档及其引用的内容），处理方式相同。
   会话已有对话时可勾选"附带最近对话"作为背景（默认勾选），开始澄清时取一次快照。原文只是起点，最终输出调整后的需求。
3. **问什么**：换任何一个 Agent 来做都知道怎么做的，就不问；只有需要用户拍板的才确认。不做硬性分类，不设格式检查，
   由 Agent 按这条判断。
4. **逐轮调查**：每轮一次真正的单次调用，先查项目再给出一个问题；每轮都带上之前所有已确认的内容
   （原需求、每个问题与回答、前几轮调查结论），避免片面；后面问什么取决于前面的回答与项目实际情况。
5. **广度与深度**：首轮列出所有待确认的方向，之后每轮深入一个；每次回答后重新审视整个列表，去掉不再需要的，
   加上新引出的并说明来源。用户可以跳过某个方向（按默认处理）、指定先问哪个、自己添加方向。
6. **先质疑出发点、敢于反驳**：查实不该做或做不通就直说，附代码证据与替代做法；出发点最先问。用户可以接受，
   也可以坚持；坚持时尊重，不再纠缠。
7. **确认的形式**：2～4 个真正不同的选项，标出推荐并附理由与依据；每个选项旁写明选了它方向就定为什么；
   另有"其他想法"原话照录；也可以跳过，按事先写明的默认处理。
8. **不加门槛**：首轮同屏给出理解、方向列表、第一个问题，回答即继续；理解偏了可以"纠正理解"随回答提交；
   首轮没有需要确认的方向就直接给结果；随时可以"够了，生成结果"；除回答问题外没有任何确认步骤。
9. **守住用户的决定**：用户的回答、跳过、先问这个、添加的方向、纠正都由插件保存，模型任何一次返回（包括在途那一轮）
   都不能覆盖。不设硬性上限，由 AI 判断何时停：问透就停、不重复问、没有需要确认的就结束；但不能无限追问。
   只有用户的回答、原话或跳过才算定下了方向；没定的不会被当成用户同意。
10. **输出**：只输出调整后的需求——原需求与已确认方向融合，精炼，只到方向层，不附带任何其他内容。
    窗口里可编辑；点"交给 Agent"后按结对编程的时机发送并提交：主会话正在执行或停在确认框上时，等这一轮结束再发，
    其余情况立即发；终端暂时不能接收时持续重试，可取消；会话标签页已关闭或终端已结束时停止并提供复制。
    不写文件，不修改原文档。（与用户逐条确认时为"任何时候都直接发"，评审后按用户要求改为与结对编程对齐。）
11. **技术方式**：IDEA 原生非模态窗口，每会话一个；入口在横幅「单次审查」旁与终端右键菜单；沿用轨迹的单次后台调用，
    固定使用当前会话的 Agent 类型，最大权限，"不改文件"只靠提示词；每轮可取消，超时 600 秒可重试；
    吸收 brainstorming 方法论为内置中英提示词，随插件发布，注明出处与 MIT 许可；状态按会话保存在内存，
    关窗不中断在途一轮，关标签页清理，不跨 IDE 重启，会话切换新 ID（`/clear`、`/new` 等）时保留。
12. **文档写法**：只写方向与方案、数据流转、组件与必须守住的性质；不列测试用例；实现状态如实写；
    设计者自行决定的单列一节；旧 HTML 原型（`docs/prototypes/requirement-clarifier.html`）已作废，不作为依据。

以下各节是这 12 条的具体设计。

## 方案选择（Approaches）

### 多轮上下文如何延续

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A. 每轮新调用 + 插件持有台账（采用）** | 每轮一次全新的单次调用；插件保存原需求、方向列表、问答记录和调查笔记，每轮完整交给 Agent | 三种 CLI 一致；不产生会话文件；满足第 4 条"带上所有已确认内容" |
| B. 保存会话并续接 | 去掉不落盘参数，用 `--resume` / `exec resume` 续接 | 会话文件会被 imux 的会话监控扫到、出现在会话列表；三种 CLI 续接方式各异 |

### 澄清方法论如何交给 Agent

| 方案 | 取舍 |
|---|---|
| 原样加载 obra/superpowers 的 brainstorming 技能 | Codex 无单次加载参数；技能是否被调用由模型决定；原版要求等用户回复、写设计文档并提交 git，与单次最大权限调用冲突 |
| **吸收为内嵌指南，拼进提示词（采用）** | 三种 CLI 走同一条 stdin 路径；内容确定；资源随插件 jar 分发，`runIde` 与正式安装都可用 |

## 流程

```text
输入需求（一句话 / 一段 / 文档路径）
  → 首轮：调查 → 我的理解 + 方向列表 + 第一个问题（同屏）
        └ 没有需要确认的方向 → 直接生成调整后的需求
  → 逐轮：用户回答 → 调查（带上全部已确认内容）→ 重审方向列表 → 下一个问题，或结束
  → 生成调整后的需求 → 用户可编辑 → 交给 Agent（发送并提交）
```

## 台账：插件持有

插件保存以下内容，每轮完整交给 Agent；Agent 的返回只是提议，由插件校验后合并。

- **原需求**：用户输入原样保存（文档路径时保存路径，由 Agent 读取）。
- **背景快照**：勾选时，开始澄清时截取的会话最近对话（上限 8,000 字符）。读取逻辑需从 `PeerCoordinator` 的私有方法
  `collectLatestConversation` 抽成可复用函数。
- **我的理解**：首轮 Agent 的复述；用户的纠正原样附在后面。
- **方向列表**：每个方向有稳定 ID、标题、为什么需要用户确认、跳过时的默认处理、状态、已有结论与剩余疑点、
  是否为用户添加。
- **问答记录**：每个问题、所属方向、选项、用户的选择或原话、是否跳过。
- **调查笔记**：Agent 每轮给出的完整新版本，替换上一轮（上限 6,000 字符）。

### 方向状态

| 状态 | 含义 | 由谁改变 |
|---|---|---|
| 待确认 | 还没定 | Agent 新增、用户添加；Agent 换去问别的方向时，未定的方向保持待确认并记下已有结论与剩余疑点 |
| 当前 | 正在问的方向，任一时刻至多一个 | 插件在展示问题时设置 |
| 已定 | 用户回答或给出原话后，Agent 判断已经说清 | Agent 提议，插件校验（必须有对应的用户回答） |
| 按默认 | 用户跳过，采用事先写明的默认处理 | 用户 |
| 已去掉 | 因为某个回答或发现不再需要确认，附理由 | Agent 提议，插件校验 |

### 用户操作优先（第 9 条）

| 操作 | 规则 |
|---|---|
| 回答、"其他想法"原话、纠正理解 | 原样保存，Agent 不能改写 |
| 跳过 | 该方向冻结为"按默认"，Agent 不能再改它，也不能再就它提问；只有用户"重新打开"能解冻 |
| 先问这个 | 下一轮的问题必须针对该方向；问题展示出来后指定解除 |
| 用户添加的方向 | Agent 不能去掉它；只能就它提问，由用户的回答来定 |
| Agent 调查期间的操作 | 先暂存，结果返回后合并；若返回的问题因此失效（如针对刚被跳过的方向），丢弃并用新台账立即重新调用一次 |

## 协议

### 插件 → Agent（每轮提示词）

1. 内嵌指南正文（去掉 front matter）；
2. 本阶段说明（首轮 / 逐轮 / 生成结果），由 Kotlin 代码按语言生成；
3. 台账全部内容，以及本轮约束：必须针对的方向（用户"先问这个"时）、冻结的方向；
4. 输出格式与"只输出 JSON、不修改任何文件"。

### Agent → 插件（首轮与逐轮）

```json
{
  "understanding": "要做什么、为什么做；代码现状与这次会碰到哪里（仅首轮与用户纠正理解后的那一轮）",
  "directions": {
    "add": [{"tempId": "new-1", "title": "……", "why": "为什么需要用户确认", "source": "来自哪个回答或哪处代码",
             "fallback": "跳过时的默认处理"}],
    "drop": [{"id": "d3", "reason": "……"}]
  },
  "previous": {"id": "d1", "status": "DECIDED", "conclusion": "……", "openPoints": []},
  "notes": "调查笔记（完整新版本）",
  "next": {
    "type": "question",
    "directionId": "new-1",
    "question": "……", "reason": "……", "basis": "代码位置等依据",
    "options": [
      {"id": "a", "label": "……", "recommended": true, "conclusion": "选了它，方向就定为……"},
      {"id": "b", "label": "……", "recommended": false, "conclusion": "……"}
    ]
  }
}
```

- `previous`：上一轮出过问题时必填，说明上一轮那个方向现在是"已定"还是仍"待确认"（附已有结论与剩余疑点）。
- `next.type` 为 `question` 或 `done`。`done` 时附 `requirement`：调整后的需求全文。
- **临时 ID**：新增方向用本次返回内有效的临时 ID（`new-` 开头、不重复），`next.directionId` 可以引用它；
  插件合并时分配稳定 ID（`d1`、`d2`……，用户添加的为 `user-1`……）并替换引用。`directions.drop`、`previous.id`
  只能引用已有稳定 ID。
- 校验不通过（JSON 无效、引用不存在、问题针对冻结或已定的方向、未遵守"先问这个"、选项不是 2～4 个、选项缺少
  `conclusion`、去掉用户添加的方向）：在提示词末尾附错误重新调用一次；仍失败显示 Agent 原文，提供"重试"与"生成结果"。

### 生成结果

- Agent 返回 `done` 时，直接使用其中的 `requirement`。
- 用户点"够了，生成结果"：调用一次"生成结果"阶段，只返回 `{"requirement": "……"}`。
- 生成规则（写进阶段说明与指南）：把原需求与所有"已定""按默认"的方向融合成一份需求；精炼，只到方向层；
  不附带任何说明、依据、未决事项或标记；没定的方向不写成已定。
- 失败页的"生成结果"不调用 Agent：插件把原需求与已定、按默认的结论按顺序拼接成文本，供用户编辑后发送。

## 交付（第 10 条）

时机与结对编程对齐——结对编程只在主会话这一轮结束后才注入，从不在执行中或确认框上插话：

| 主会话状态 | 判定 | 处理 |
|---|---|---|
| 执行中 | 会话 ID 在 `SessionMonitor.runningIds` 中 | 进入"等待当前回合结束"：发送循环每 500ms 重读这两个信号，主会话不再执行、也不停在确认框上时发送 |
| 停在权限确认或选择框 | Claude 运行态 `ClaudeRuntimeSession.isWaiting` | 同上，等这一轮结束再发；Codex / Pi 无此信号，与结对编程同一盲区 |
| 其余 | — | 立即发送 |

- 不挂在 `SessionMonitor` 的轮次完成事件上，而是在发送循环里轮询 `runningIds` / `isWaiting`：
  确认框被 Esc 取消、直接回到空闲时没有轮次完成事件，挂事件会一直等下去。
- 发送复用结对编程的 `trySendPeerFeedback`（括号粘贴 + 回车同一次发送）；括号粘贴未开启时每 100ms 重试，与 `PeerCoordinator.injectFeedback` 相同。
- 等待与重试期间窗口显示状态并提供"取消发送"，取消后回到结果页。
- 会话标签页已关闭、或终端视图已不存在时停止，弹通知并提供复制；标签页关闭时澄清停在结果页或发送中，同样先通知并提供复制再丢弃状态。
- 发送成功后窗口关闭，该会话的澄清状态清空。

## 窗口交互

- 非模态 `DialogWrapper`，每个会话最多一个；再次点击入口聚焦已有窗口。
- 入口：顶部横幅「单次审查」旁的 `ActionLink`「需求澄清」（与「单次审查」同时显示和隐藏）；终端正文右键菜单「需求澄清」。
- 布局（`JBSplitter` 两栏）：
  - 左栏：原需求；方向列表（`JBList`，状态图标用 `AllIcons`，已定的显示结论）；右键"跳过""先问这个""重新打开"；
    底部"+ 添加方向"。
  - 右栏按状态切换：

| 右栏 | 显示 | 操作 |
|---|---|---|
| 输入需求 | 多行文本框（可填一句话、一段或文档路径）；"附带当前会话最近对话" | 开始澄清 |
| 调查中 | 复用轨迹的进度显示（当前工具、已用时间） | 取消；仍可跳过、先问这个、添加方向（暂存） |
| 问题 | 首轮上方为"我的理解"；问题、理由、依据；选项与各自的结论，标出推荐；其他想法 | 确认、跳过、纠正理解 |
| 结果 | 调整后的需求，可编辑 | 交给 Agent、复制、返回继续澄清 |
| 失败 | 错误信息，可展开 Agent 原文 | 重试、生成结果 |

  - 底部：轮次、"够了，生成结果"、"关闭"。

**生命周期**

- 关闭窗口不取消在途一轮；状态由 `ClarificationService` 按 `sessionKey` 保存在内存，重新打开时恢复。
- 会话标签页关闭：取消并清理进程，丢弃状态。
- 会话 key 迁移（`TerminalHost.addSessionKeyMigratedListener`，pending 绑定、`/clear`、`/new` 都会触发）：
  把澄清状态迁到新 key，在途一轮继续执行，结果写入新 key。不能照搬 `PeerCoordinator.migrateSessionKey`，
  它会终止在途调用。
- 每轮超时 600 秒（与轨迹相同），取消、超时都可以重试本轮。

## 必须守住的性质

具体测试用例由实现方按 `AGENTS.md` 的测试规范自行设计。

1. **用户操作优先**：回答、原话、跳过、先问这个、添加的方向、纠正，不会被任何一次模型返回（包括在途一轮）覆盖。
2. **选中即记下**：用户选中一个选项，记下的结论与界面上该选项显示的结论一致。
3. **没定的不算已定**：只有用户的回答、原话或跳过能让方向定下；生成结果时，没定的方向不写成已定。
4. **每轮带上全部已确认内容**：每次调用的提示词都包含完整台账。
5. **临时 ID 正确映射**：同一次返回中新增多个方向时，问题引用的是对应那一个的稳定 ID。
6. **输出只有需求本身**：交给 Agent 的文本就是窗口里显示（及用户编辑后）的调整后需求，不附带任何内容。
7. **不加门槛**：首轮没有需要确认的方向时直接给结果；除回答问题外没有确认步骤。
8. **会话 key 迁移不丢状态**：迁移后状态与在途一轮都保留。

## 调整：照 Claude Code 的提问过程（用户后续要求，取代此前的"一批问题 + 单栏界面"方案）

用户试用后指出：窗口功能复杂冗余、反复渲染导致卡顿；要像 Claude Code 那样逐步让用户选择，直到路线可行——有时几个问题一起问，有时问一个再思考。以下覆盖第 4、5、7、8 条中与之不一致的表述，其余要求不变。

## 调整：同一个澄清 Agent 连续对话（用户后续要求，取代"每轮新调用 + 插件持有台账"）

用户要的是 Claude Code 的**内部流程**：Agent 在同一次持续的对话里边查边想，需要用户拍板时停下来提问，拿到回答后带着已有的思考和上下文接着做，可能再问，直到方向可行。此前"每轮启动全新单次进程、整份台账重喂"的做法慢且不连贯，予以取代。智能体仍固定跟随当前会话（用户确认）。

### 进程与会话
| CLI | 连续对话方式 | 落盘 |
|---|---|---|
| Claude | 常驻进程 `claude -p --input-format stream-json --output-format stream-json --verbose --no-session-persistence`（权限与 IDEA MCP 同单次调用），每轮经 stdin 发一条 user 消息，读到本轮 `result` 为止 | 不落盘 |
| Pi | 常驻进程 `pi --mode rpc --no-session`（IDEA MCP 扩展同单次调用），按 RPC 协议发消息、读到本轮结束 | 不落盘 |
| Codex | 首轮 `codex exec --json …`（不加 `--ephemeral`），取得会话 ID；之后每轮 `codex exec resume <id> --json …` | 落盘为 `exec` 来源，imux 本就不列非交互会话；澄清结束时删除该会话文件 |

- **开始**：点「开始澄清」启动；整个澄清只用这一个对话。「继续澄清」沿用同一对话。
- **结束**（任一）：**关闭窗口**（用户要求：残留的以后也用不上）；「交给 Agent」发送成功；会话标签页关闭；项目关闭。结束时终止进程、清空澄清状态，Codex 的会话文件一并删除。已有回答或未发送的结果时，关闭前确认一次，避免误关丢掉。
- 不保留、不恢复：没有空闲超时，也没有关窗后接着聊。
- **取消**本轮：结束进程（Claude/Pi）或放弃本轮（Codex），已确认的问答保留；之后重试或继续时新开一个对话，把原需求与已确认的问答作为开场交给它接着做。

### 每一轮
- 首条消息：内嵌指南 + 规则 + 原需求 + 背景快照 + 输出格式。之后每条消息只发这一批的回答（问题短标签 → 回答；跳过的写明按默认处理），以及一句格式提醒。
- Agent 每轮以 JSON 结束：1～4 个问题，或"完成"（附调整后的需求）。格式不合规时，在同一对话里把错误发回让它重答一次，仍不合规进入失败页。
- 已确认 = 用户的回答（含跳过时的默认处理），由插件按问答记录直接得出，用于界面上的已确认列表、失败兜底与取消后新开对话时的开场；不再要求 Agent 逐条交代方向状态。
- **没有「够了，生成结果」按钮**（用户要求去掉）：何时结束由 Agent 判断，方向清楚了就直接给出调整后的需求；用户不想继续就关闭窗口。本文前面各节中关于「够了」的表述均以此为准。失败页保留不调用 Agent 的「生成结果」（原需求 + 已确认的问答）。
- Codex 会在它自己的 `state_5.sqlite` 里留下一条指向已删会话文件的 exec 记录；imux 不读该库、Codex 默认列表也不显示 exec 来源，不做处理。

## 调整：定位扩展与命名「先聊再做」（用户后续确认）

**定位**：开工前的引导者。用户只有一个目标——任何想让 Agent 做的事（改文件、改代码、完善需求、头脑风暴、出方案……），中间步骤和要考虑的方面可以完全不知道。引导 Agent 懂项目代码、懂项目里的文件与系统，需要时借助网络知识，顺着用户的目标一步一步提问（只问需要用户拍板的方向，给选项与推荐），每次回答后接着想、接着查，把没考虑到的方向全部补上，方向清楚了自己结束。产出是一份**执行方案**：从目标出发、由问答定下的可执行方向性指引，既在用户脑中建立清楚的执行思路，也发给当前会话的 Agent 去执行。仍只到方向层、不改文件。本文前面各节中的"需求澄清 / 调整后的需求"均按此理解。

## 调整：共同探究与多种回应形式（2026-10-23，取代固定成果分类）

用户希望像与善于深入探讨的哲学家交流：有独立判断，能审视前提与概念、提出解释并接受反驳，

## 由设计者（Claude）决定、用户未明确表态的事项

- 每轮新调用、插件持有台账，而不是续接 CLI 会话。
- 方向不分类型；"先质疑出发点"只写在指南里，由 AI 判断，插件不强制排序。
- 调查笔记 6,000 字符、背景快照 8,000 字符的上限。
- 校验失败自动重试一次；失败页的"生成结果"由插件拼接、不调用 Agent。
- 发送成功后关闭窗口并清空该会话的澄清状态。
- 发送时机与结对编程对齐的判定方式（`runningIds` 与 Claude `isWaiting`），在发送循环里轮询这两个信号，而不是挂在 `SessionMonitor` 轮次完成处。
- 背景快照在 IO 线程读取；窗口只在状态切换时重建右栏，避免刷新清掉正在输入的内容。
- 编辑器关闭时用 `serviceIfCreated` 取服务，项目关闭时服务关闭仍打开的窗口。
- 横幅里的「需求澄清」始终显示：结对编程开启后仍在；"不再提示"只收起结对编程自己的内容，横幅保留一条只含「需求澄清」的细条。
- 指南要求只读调查：不改文件、不运行构建或测试、不启动服务（仍只是提示词约束，权限不变）。
- 提示词里答过的题只带问题与记下的结论，不再带选项。
- 跳过的方向冻结、用户添加的方向不能被 Agent 去掉、"先问这个"出题后解除。
- 已定的方向、用户刚回答的方向、"先问这个"的方向也不能被 Agent 去掉；去掉的方向在列表里灰显并附理由。
- 离开问题页而未回答（生成结果、继续澄清）时，被问的方向回到待确认，之后仍可被问。
- 用户指定了"先问这个"、或调查期间改过方向时，Agent 返回 done 不被接受：前者附错误重调，后者用新台账直接重调。
- "够了，生成结果"在问题页与调查中可用，调查中点击会作废在途一轮；"取消"只在调查中生效。
